# RomanVoice full audit, 2026-07-13

Status: complete read-only audit of the live PC and plugged-in Pixel, plus a
source, dependency, security, custody, and reliability review of the canonical
repository.

The audit follows `docs/NORTH_STAR.md`, created during this review. No phone
setting, token, firewall rule, startup item, runtime code, Git history, or remote
state was changed. The Android APK was rebuilt and verified locally. Generated
build output remains ignored by Git.

## Executive conclusion

The July 12 failure was caused by a home-LAN endpoint on a cellular phone, with
Tailscale disconnected. It was not caused by OAuth, a token mismatch, a dead PC
service, a microphone denial, an accessibility failure, an Android crash, or a
duplicate RomanVoice process.

The phone was configured with:

```text
ws://192.168.1.232:8799/v1/transcribe/stream
```

At 2:19:54 PM EDT the screenshot shows 5G and no Wi-Fi or VPN. A private
`192.168.x.x` address is not reachable from cellular. The Pixel had no active
Tailscale process, VPN interface, or always-on VPN. The PC and phone bearer-token
fingerprints match.

This was preventable. The installer silently fell back to the LAN address on
July 9, and the shipped health checker still certifies that exact home-only
configuration as healthy. A prior manual Tailscale repair therefore did not
survive reprovisioning.

## Prioritized findings

### P0. Provisioning can silently recreate the exact outage

Evidence:

- `clients/android-ime/install-to-connected-phone.ps1:45-88` prefers Tailscale
  but silently selects the first LAN address when Tailscale resolution fails.
- The installer overwrites all phone preferences at lines 107-113 and 188-200.
- The live phone preference was written during the July 9 reinstall and is
  LAN-only.
- `scripts/check-phone-tile-health.ps1:110-120` rejects loopback and a literal
  placeholder, but accepts RFC1918 LAN addresses such as `192.168.1.232`.
- The live command below exits zero and reports the broken configuration as OK:

```powershell
.\scripts\check-phone-tile-health.ps1 -RequireAdbDevice
```

Required repair:

1. Fail closed when a Tailscale address is unavailable.
2. Permit LAN provisioning only through explicit `-PreferLan` intent.
3. Preserve an existing valid Tailscale endpoint during reinstall.
4. Add explicit normal and LAN-only health modes.
5. In normal mode, reject RFC1918 endpoints, verify the configured phone
   endpoint, inspect phone VPN transport, compare token fingerprints, and prove
   actual endpoint reachability.
6. Require a cellular-only real-device smoke test before an Android release is
   considered ready.

### P0. Installer leaves the bearer token in persistent staging files

Evidence:

- `clients/android-ime/install-to-connected-phone.ps1:107-113,188-200` writes
  the full preferences XML, including the bearer token, to a Windows temp file
  and an Android shell temp file.
- Both July 9 files still exist:
  - `%TEMP%\romanvoice_ime.xml`
  - `/data/local/tmp/romanvoice_ime.xml`
- The phone copy is owned by `shell:shell` and has mode `666`.
- Neither path is cleaned up.

Required repair:

1. Stage with restrictive permissions and delete both copies in `finally`.
2. Avoid a persistent shared phone temp file if `run-as` can receive the data by
   a safer path.
3. Remove the existing residues only after the corrected workflow is ready.
4. Rotate the desktop token and reprovision every client after cleanup.
5. Add a documented token-rotation and fingerprint-verification workflow.

Related token-custody risks:

- `config.py:69-99` lets `ROMANVOICE_SERVICE_TOKEN` override the file while the
  phone installer always reads the file, allowing hidden divergence.
- If token-file persistence fails, the service continues with an in-memory
  token that clients cannot discover after the fact.
- The installed Android app is debuggable and stores the token in ordinary
  private SharedPreferences. The protected app-data parent and SELinux reduce
  exposure, but an authorized ADB shell can extract it.

### P1. Ready is not end-to-end ready

Evidence:

- `RomanVoiceTileService.java:48-99` reports `READY` from the local
  accessibility-service phase. It does not prove PC reachability, VPN state,
  endpoint suitability, token acceptance, microphone readiness, or insertion.
- An `ERROR` phase falls through to `READY`.
- `RomanVoiceFloatingService.java:859-884` puts most state in an accessibility
  content description rather than persistent visible text.
- A connection failure shows a transient toast, then resets to a green `Start`
  state after three seconds.
- `RomanVoiceFloatingService.java:970-982` normally reports
  `available=true`, including connection and stream failures. The host can
  therefore interpret a recent failed heartbeat as healthy.
- The heartbeat is host-facing and cannot tell Roman, while away from home, why
  the phone is not ready.

Required repair:

- Add persistent, distinct states for LAN-only configuration, VPN unavailable,
  PC unreachable, authentication rejected, microphone unavailable, focused
  field unavailable, and end-to-end ready.
- Perform an authenticated preflight before recording.
- Preserve the last failure until a successful preflight or deliberate retry.
- Track last successful stream and last successful insertion separately from
  heartbeat freshness.
- Keep a small privacy-safe on-device ring log containing phase, endpoint class,
  transport class, error category, and insertion result, never token, audio, or
  transcript content.

### P1. The floating workflow lacks a reliable visible cancel path

Evidence:

- `RomanVoiceFloatingService.java:39` keeps `SHOW_CANCEL_BUTTON = false`.
- Long-press cancel exists but is not discoverable.
- During connecting and finishing, the overlay is disabled and tile taps are
  ignored.
- Finalization may wait as long as 90 seconds.

This violates the North Star rule that Android dictation must have an explicit
cancel path. A visible cancel control should remain available throughout
connecting, recording, and finishing, and the tile should have deterministic
cancel or abort behavior in those phases.

### P1. Floating insertion can overwrite unrelated text or the wrong field

Evidence:

- `RomanVoiceFloatingService.java:629-743` reacquires the currently focused
  editable node for each partial and rewrites the entire field with
  `ACTION_SET_TEXT`.
- A session does not retain a stable package, window, or view identity.
- `RomanVoiceTextRange.java:21-42` can accept old coordinates because their
  length matches even when the contents at those coordinates changed.
- `tests/test_android_text_range_java.py:67-75` currently treats overwriting a
  changed phrase as valid behavior.
- If range relocation fails, a later partial can use the current selection and
  duplicate or misplace dictation.
- Cancel reacquires the current field and can delete a matching phrase from a
  different target.
- A final empty result can remove the latest non-empty partial rather than keep
  the best available text.
- Whole-field replacement can damage spans or application-managed formatting.
- The hardcoded `RCS message` placeholder rule can discard legitimate text with
  that exact value.

Required repair:

- Bind the session to a stable target fingerprint.
- Fail safely when focus or target identity changes.
- Require content equality before replacing a tracked range.
- Preserve the latest non-empty partial when final output is empty.
- Add a real Google Messages attachment-caption scenario, including preexisting
  caption text, focus changes, cancel, and a late final.

### P1. Network transitions and audio failures can leave the UI stuck

Evidence:

- `RomanVoiceStreamClient.java:149-177,202-227` handles a graceful server close
  by marking itself closed and returning without a terminal listener callback.
  The UI can remain in `RECORDING`, audio can continue to be read and discarded,
  and stop can wait for the 90-second final timeout.
- The close method can return early without closing the socket after a peer
  close.
- Negative `AudioRecord.read()` results are ignored in both the floating and IME
  audio loops.
- Reader threads are not joined or generation-guarded before `AudioRecord` is
  released, allowing stop-time races and late exceptions.

Required repair:

- Route every unexpected close through one session-scoped terminal callback.
- Close the socket, stop audio, and move visibly to a recoverable error.
- Treat negative audio-read codes as explicit failures.
- Use a shared, generation-guarded session controller and join worker threads.

### P1. Service exposure is broader than the North Star requires

Live state:

- RomanVoice listens on `0.0.0.0:8799`.
- Active Ethernet networks are classified Public.
- A `pythonw.exe` Public-profile rule allows any remote to reach every TCP and
  UDP port owned by Python 3.12.
- The explicit RomanVoice TCP 8799 rule is Private-only and is not what enables
  the current home-LAN path.
- HTTP and WebSocket traffic are cleartext. Tailscale encrypts the intended
  `100.x` path, but LAN fallback does not.
- `services/dictation_service.py:158-170` exposes a small unauthenticated
  `/health` response. Detailed health, phone status, heartbeat, batch audio, and
  streaming remain bearer-authenticated with constant-time comparison.

Required repair:

- Replace the broad Python firewall allowance with a RomanVoice-specific TCP
  8799 scope for the intended Tailscale and, only if needed, trusted home path.
- Check other Python applications before removing a shared rule.
- Keep public router port forwarding unsupported.
- Restrict the unauthenticated health probe to loopback or authenticate it.
- Keep bearer auth. OAuth is not needed for the current single-user private
  network. A public relay, multi-user identity model, or shared service would
  require a new security design.

### P1. Source and release custody have substantial rot

Live state:

- Local `main` at `e59f399` is three commits ahead of live `origin/main` at
  `fe14e28`.
- Six runtime and test files contain uncommitted June 28 reliability changes.
- The live process started July 8 and is executing that dirty tree.
- A checkout loss, cleanup, or fresh clone would lose production behavior.
- The fork has no test CI. Its only workflow is an inherited clone-statistics
  job still aimed at `Knuckles92/OpenWhisper`, and it has no runs in the fork.
- The Android daily build is always `versionCode 1`, `versionName 0.1.0`, and
  debuggable. The values are duplicated in Gradle and the manual builder.
- The installed APK matches the locally built APK, but package metadata cannot
  identify a release, source revision, or build time.

Required repair:

1. Preserve and validate the existing dirty reliability work.
2. Split runtime/tests, North Star/audit docs, and later remediation into clean,
   reviewable commits.
3. Push the three existing commits and reviewed new commits to the fork.
4. Add Windows Python tests and Android build/static checks to CI.
5. Use one Android version source, a monotonically increasing version code, and
   visible Git/build provenance.
6. Separate daily release and debug provisioning builds.

### P2. Startup ownership is currently healthy but not robust

Good current state:

- One real RomanVoice interpreter owns port 8799. The second Python process is
  the virtual-environment launcher, not a duplicate app.
- The Startup-folder VBS points to this canonical checkout.
- No conflicting scheduled task is active.
- Hidden startup, the watchdog, and Win32 hotkeys were healthy at the incident.

Risks:

- `scripts/ensure-romanvoice-running.ps1:92-95` can keep accepting a preferred
  process even if it never opens port 8799.
- Manual launchers lack a single-instance mutex.
- A partial watchdog installation can leave both scheduled-task and VBS paths.
- `startup-watchdog.log` is unrotated and already about 5.8 MB.
- Multiple inherited OpenWhisper launchers and installers remain, some of which
  describe the obsolete `venv` and upstream naming rather than the `uv` runtime.

Required repair: use authenticated health after a startup grace period, add a
single-instance mutex, make watchdog installation transactional, rotate or
quiet no-op watchdog logs, and deprecate stale launchers only through the
required unship-approval process.

### P2. Protocol hardening and attribution are incomplete

- `services/websocket_protocol.py:55-74` reads the peer-declared frame length
  before applying a frame cap. The service aggregate limit is enforced later at
  `services/dictation_service.py:908-924`.
- There is no socket idle timeout or connection-count limit.
- The server accepts unmasked client frames and does not fully validate the
  WebSocket handshake subset.
- The Java client does not validate `Sec-WebSocket-Accept`, and its header/frame
  readers have no explicit size limits.
- Request logging is DEBUG-only at `dictation_service.py:222-223`, so the 2:20
  WebM client cannot be attributed.

Required repair: cap declared frames before allocation, add idle and concurrency
limits, harden handshake validation, and log endpoint, source address, status,
duration, and a non-secret client/build identifier without audio or text.

### P2. Build, dependency, and platform staleness is manageable but real

- The Pixel runs Android 16/API 36 while the app compiles and targets API 35.
  The APK works and API 35 still meets the currently published Play baseline,
  but Android 16 compatibility scenarios are not tested.
- The project declares Android Gradle Plugin 8.7.3 while current official
  Android documentation shows the 9.x line. The normal script bypasses Gradle
  and hardcodes SDK/build-tools 35, creating two drifting build definitions.
- Java compilation reports two deprecated APIs:
  - `AccessibilityNodeInfo.recycle()`
  - `TileService.startActivityAndCollapse(Intent)`
- `pyproject.toml` and `requirements.txt` duplicate broad constraints. `uv.lock`
  is deterministic and current, but the secondary file is not marked generated.
- The environment has 26 newer package releases available, including
  CTranslate2. The tested Faster-Whisper/CTranslate2/CUDA pins are intentional
  compatibility constraints and should not be upgraded blindly.
- A live vulnerability audit found no known Python dependency vulnerabilities.
- OpenAI remains a mandatory dependency and API model names remain visible even
  though local Faster-Whisper is the product default. Removing or hiding a
  shipped cloud surface requires `UNSHIP_APPROVED` with reason, date, and
  decision-maker.

### P3. Duplication and general code hygiene are not incident drivers

- Clone analysis found 0.78 percent duplicated lines overall and no Java clone
  blocks at the selected threshold.
- The meaningful Android duplication is structural rather than copy-identical:
  the floating and full-IME services independently implement connection,
  recording, audio pumping, watchdog, stop/final, and cleanup state machines.
- Ruff reports 431 findings, mostly inherited formatting, import order, and
  modern-typing cleanup. There is no enforced lint baseline.
- Vulture found five high-confidence unused variables/imports.
- Mnemo's generic SQL-injection alert for `config.py:123` is a false positive;
  that line is a logging format string.
- Diagnostic audio retention currently holds the last phone stream, the latest
  batch copy, and ten rotating batch uploads. About 62 MB is present. Retention
  is bounded but not explained as a privacy or cleanup policy.

These should be handled after the end-to-end and custody work. A broad cleanup
must not obscure the reliability fixes or unship inherited behavior silently.

## Remediation order

1. Fix secret staging cleanup, remove the two residues, rotate the token, and
   reprovision every client.
2. Make Tailscale endpoint provisioning fail closed, restore the phone to
   `ws://100.92.44.49:8799/v1/transcribe/stream`, reconnect Tailscale, and decide
   whether Android always-on VPN is compatible with Roman's other VPN use.
3. Make the health gate reject this exact broken state and require a real
   cellular-only focused-field test.
4. Add persistent preflight and error states plus a visible cancel path.
5. Fix target-bound insertion, unexpected WebSocket close handling, and audio
   loop races with behavioral tests.
6. Narrow firewall exposure and harden transport/protocol limits.
7. Add Android build identity and CI, then commit and push the validated local
   production state.
8. Address startup resilience, stale inherited surfaces, dependencies, lint,
   and low-priority duplication separately.

## Feature Gate for implementation

No runtime remediation was implemented during this audit. Before coding, use
this gate:

- Goal: phone dictation is visibly and verifiably ready at home and on cellular,
  never silently home-only, with safe auth custody and no text corruption.
- Repo reality: the live app uses a dirty tree, local main is ahead of origin,
  the phone was reprovisioned to LAN, and the current health script is false
  green. Preserve all existing user changes.
- Known-good precedent: the supported transport is the current PC Tailscale
  endpoint and bearer-authenticated desktop service. Keep the desktop tray
  process as owner and copy that shape.
- Rules: local Faster-Whisper, no public gateway, bearer auth, Tailscale off-home,
  Gboard plus floating insertion, explicit cancel, no duplication, and no token
  in logs or staging residue.
- Risks: rotating a token without reprovisioning every client, removing a shared
  firewall rule used by other Python apps, enabling always-on Tailscale when
  another VPN is needed, focus drift, and confusing LAN-only developer mode with
  production readiness.
- Scenario titles: Cellular ready; LAN-only rejected; VPN unavailable explained;
  Auth rejected explained; Reinstall preserves Tailscale; Temp secrets removed;
  Connect canceled; Finish canceled; Network switch fails safely; Focus change
  preserves unrelated text; Empty final keeps best partial; Health gate proves
  end to end.
- Open questions: whether another Android VPN must coexist with Tailscale, what
  surface originated the 2:20 WebM request, and whether inherited OpenAI/cloud
  surfaces remain supported.
